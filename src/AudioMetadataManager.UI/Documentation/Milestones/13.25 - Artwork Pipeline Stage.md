# Milestone 13.25

## Conexión real de la carátula al pipeline modular

## Objetivo

Convertir `TrackArtworkService` (milestone 13.24) en una quinta etapa
real del pipeline modular de aplicación de metadatos
(`MetadataApplicationPipelineFactory`), en lugar de un servicio
independiente sin conexión.

Este milestone lleva la carátula al mismo nivel de integración que ya
tienen Validation, Backup, Writing y Verification: parte de la
composición por defecto, auditada como cualquier otra etapa, y
reutilizando el respaldo verificado que crea la etapa de Backup.

## Nota importante sobre "pipeline real"

El pipeline modular por etapas (`MetadataApplicationPipelineExecutor`
+ `MetadataApplicationPipelineFactory`, construido en los milestones
13.15-13.20) **todavía no está conectado a `MainWindow`**. La
aplicación real usa hoy una clase monolítica anterior,
`MetadataApplicationPipeline` (`Services/Simulation/Application/Pipeline/MetadataApplicationPipeline.cs`),
instanciada directamente en `MainWindow.xaml.cs`.

Esto no es una limitación de este milestone: ninguna de las cuatro
etapas existentes (Validation/Backup/Writing/Verification) está
conectada a `MainWindow` tampoco. El patrón establecido por el propio
proyecto en los milestones anteriores fue construir el pipeline
modular completo primero, probarlo a fondo, y dejar la migración de
`MainWindow` desde la clase monolítica como un milestone separado
todavía pendiente. La carátula queda exactamente en ese mismo estado:
completa, probada, real, pero a la espera de la misma migración que
afecta a las otras cuatro etapas por igual.

## Componentes incorporados

### MetadataApplicationStage.Artwork

Nueva identidad de etapa (`Artwork = 6`), agregada al enum existente
sin modificar los valores anteriores.

### MetadataApplyRequest.ArtworkUrl

Nueva propiedad opcional, independiente de `Changes`. Una solicitud
puede pedir únicamente una carátula, sin modificar ningún otro
metadato.

`IsStructurallyValid` se relajó de `ValidChanges.Count > 0` a
`ValidChanges.Count > 0 || HasArtworkRequest`, para permitir
solicitudes de "solo carátula".

### MetadataApplyRequestValidator

El error `NO_VALID_CHANGES` ahora solo se dispara cuando no hay
cambios de campo **ni** una carátula solicitada.

### MetadataWritingStage

Se agregó una comprobación temprana: cuando la solicitud no tiene
cambios de campo válidos (por ejemplo, una solicitud de solo
carátula), la etapa construye directamente un
`MetadataWriteResult` con estado `NoWritableChanges` **sin invocar al
escritor real**, reutilizando exactamente el mismo camino que ya
existía para ese estado. `MetadataVerificationStage` ya sabía omitirse
correctamente ante `NoWritableChanges`, así que no requirió cambios.

Sin este ajuste, una solicitud de solo carátula habría fallado en la
etapa de escritura (`MetadataWriteRequest.IsStructurallyValid`
también exige cambios de campo) antes de llegar siquiera a la nueva
etapa de carátula.

### MetadataArtworkStage

Quinta etapa concreta, orden de ejecución `500`.

- Si la solicitud no pide carátula: `Skipped`, sin tocar nada.
- Si no existe un respaldo verificado: `Failed` (misma
  comprobación que ya usa `MetadataWritingStage`).
- Descarga e incrusta la carátula mediante `TrackArtworkService`,
  reutilizando `context.BackupResult.BackupFilePath` como respaldo
  verificado — no crea un segundo respaldo.
- Éxito → `Completed`; cancelación → `Cancelled`; cualquier otro
  fallo (descarga o incrustación) → `Failed`.

### MetadataApplicationContext / MetadataApplicationPipelineResult

Se agregó `ArtworkResult` (tipo `TrackArtworkResult?`) a ambos,
siguiendo el mismo patrón que `BackupResult`, `WriteResult` y
`VerificationResult`.

### MetadataApplicationPipelineFactory

`CreateDefault()` ahora registra cinco etapas:
Validation(100) → Backup(200) → Writing(300) → Verification(400) →
Artwork(500).

## Verificación

### Regresión sobre la batería estructural existente

Se ejecutaron, sin modificarlos en su lógica, todos los `TestRunner`
estructurales existentes del subsistema `Simulation.Application`
mediante un proyecto de consola temporal en el scratchpad (con
`ProjectReference` al proyecto real):

- `MetadataApplicationContextTestRunner`: OK.
- `MetadataValidationStageTestRunner`: OK.
- `MetadataBackupStageTestRunner`: OK.
- `MetadataWritingStageTestRunner`: OK (el nuevo camino de "sin
  cambios de campo" no afecta ningún escenario existente, ya que
  ninguna prueba anterior construye una solicitud con cero cambios).
- `MetadataVerificationStageTestRunner`: OK.
- `MetadataApplicationPipelineExecutorTestRunner`: OK.
- `MetadataApplicationPipelineFactoryTestRunner`: actualizado para
  esperar cinco etapas, identidades, tipos concretos y órdenes de
  ejecución `100/200/300/400/500`. OK.

**Hallazgo no relacionado**: `MetadataApplicationStageBaseTestRunner`
falla en su comprobación de cancelación. Se investigó a fondo: el
archivo `MetadataApplicationStageBase.cs` no fue tocado en ningún
momento de este milestone. Se intentó una corrección (mover la
comprobación temprana de cancelación dentro del `try/catch` para que
una etapa cancelada *antes* de comenzar quede igualmente registrada),
pero esa corrección **rompe** una aserción explícita de
`MetadataVerificationStageTestRunner`, que espera exactamente el
comportamiento contrario (`StageResults.Count == 0` para ese mismo
caso). Es decir: dos pruebas estructurales ya existentes codifican
contratos incompatibles para el mismo escenario. Se revirtió el
intento de corrección para no decidir unilateralmente cuál contrato es
el correcto. **Queda como hallazgo pendiente, sin resolver, fuera del
alcance de este milestone.**

### Prueba real de extremo a extremo

Contra copias aisladas de un archivo real de la biblioteca del
usuario (`04 Sub Sub - Past.mp3`), nunca el original:

1. **Campo + carátula juntos**: las cinco etapas terminaron
   `Completed`. Se escribió y verificó un cambio de `Artist`, y se
   incrustó una carátula real descargada por HTTP (`0 -> 1` imagen).
2. **Solo carátula (cero cambios de campo)**: `Writing` se completó
   con advertencias (sin invocar al escritor real), `Verification` se
   omitió correctamente, y `Artwork` incrustó la imagen igualmente.
   Ninguna etapa produjo un fallo bloqueante.
3. **Camino de fallo real**: en una corrida, la descarga de prueba
   recibió un HTTP 429 genuino (límite de tasa de Wikimedia, por las
   descargas repetidas de este mismo archivo de prueba durante la
   sesión). La etapa lo clasificó correctamente como `Failed` sin
   excepciones, sin corromper el archivo y sin afectar las demás
   etapas.
4. En todos los casos, el hash SHA-256 del archivo **original** de la
   biblioteca del usuario permaneció idéntico antes y después.
