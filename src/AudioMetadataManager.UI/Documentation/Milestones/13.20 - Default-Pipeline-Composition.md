# Milestone 13.20

## Composición predeterminada del pipeline de aplicación

## Objetivo

Establecer un único punto de composición para construir el pipeline
predeterminado de aplicación de metadatos.

La composición debe registrar las cuatro etapas funcionales disponibles,
conservar su orden obligatorio y aplicar una configuración segura sin trasladar
la responsabilidad de construcción a `MainWindow` ni a futuros consumidores.

Este milestone valida la estructura y configuración de la composición. No
ejecuta todavía el pipeline completo sobre un archivo musical real.

## Componentes incorporados

### MetadataApplicationPipelineFactory

Centraliza la construcción del pipeline predeterminado de aplicación de
metadatos.

La fábrica es responsable de:

- crear las implementaciones concretas utilizadas por cada etapa;
- crear una instancia nueva de cada etapa;
- registrar las etapas dentro de
  `MetadataApplicationPipelineExecutor`;
- conservar el orden funcional obligatorio;
- proporcionar opciones predeterminadas seguras;
- permitir la creación con opciones explícitas;
- rechazar configuraciones nulas;
- evitar que los consumidores repliquen manualmente la composición.

La fábrica no ejecuta el pipeline, no abre archivos musicales y no conserva
estado compartido entre creaciones.

### MetadataApplicationPipelineExecutor

Cada llamada a la fábrica produce una instancia independiente de
`MetadataApplicationPipelineExecutor`.

El ejecutor recibe las etapas ya compuestas y ordenadas, junto con las opciones
que controlarán la futura ejecución.

La responsabilidad del ejecutor continúa separada de la fábrica:

- la fábrica construye la composición;
- el ejecutor coordina la ejecución;
- las etapas realizan las operaciones funcionales;
- `MetadataApplicationContext` conserva el estado compartido.

### MetadataApplicationPipelineOptions

La composición predeterminada utiliza opciones seguras para el estado actual
del proyecto.

La configuración establece:

- `StopOnBlockingFailure`: activado;
- `StopOnCancellation`: activado;
- `StopOnSkippedStage`: desactivado;
- `RejectDuplicateExecutionOrder`: activado;
- `CompleteContextAutomatically`: desactivado.

Mantener desactivado `CompleteContextAutomatically` permite incorporar
posteriormente una etapa final responsable de construir y cerrar el resultado
consolidado, sin completar prematuramente el contexto compartido.

## Composición predeterminada

La fábrica registra exactamente cuatro etapas:

1. `MetadataValidationStage`.
2. `MetadataBackupStage`.
3. `MetadataWritingStage`.
4. `MetadataVerificationStage`.

La composición conserva las identidades funcionales:

1. `Validation`.
2. `Backup`.
3. `MetadataWrite`.
4. `PostWriteVerification`.

También conserva los órdenes de ejecución:

- Validación: `100`.
- Respaldo: `200`.
- Escritura: `300`.
- Verificación posterior a la escritura: `400`.

Estos órdenes mantienen la secuencia obligatoria:

1. comprobar la solicitud;
2. crear y verificar el respaldo;
3. escribir los cambios aprobados;
4. comprobar los valores persistidos.

## Independencia entre instancias

Cada invocación de la fábrica construye objetos nuevos.

Se verificó que dos creaciones sucesivas no comparten:

- la instancia de `MetadataApplicationPipelineExecutor`;
- la instancia de `MetadataApplicationPipelineOptions`;
- las instancias concretas de las etapas.

Esta independencia evita que una ejecución futura pueda contaminar otra
mediante estado mutable compartido.

## Rechazo de opciones nulas

El método de creación que recibe opciones explícitas exige una instancia válida
de `MetadataApplicationPipelineOptions`.

Cuando se proporciona una referencia nula:

- la composición no se crea;
- no se registran etapas;
- se produce `ArgumentNullException`.

Esto mantiene explícito el contrato de la fábrica y evita construir un pipeline
con una configuración indefinida.

## Pruebas estructurales

Se incorporaron:

- `MetadataApplicationPipelineFactoryTestRunner`;
- `MetadataApplicationPipelineFactoryTestResult`.

El runner inspecciona la composición producida por la fábrica sin ejecutar las
etapas.

Por tanto, estas pruebas:

- no abren archivos musicales;
- no crean respaldos reales;
- no escriben metadatos;
- no ejecutan la verificación posterior;
- no modifican la biblioteca del usuario.

## Comprobaciones realizadas

Se validó:

- registro de exactamente cuatro etapas;
- utilización de los tipos concretos esperados;
- conservación de las cuatro identidades funcionales;
- conservación de los órdenes `100`, `200`, `300` y `400`;
- orden final de validación, respaldo, escritura y verificación;
- configuración predeterminada segura;
- independencia entre creaciones sucesivas;
- rechazo de opciones nulas.

## Integración diagnóstica temporal

`MetadataApplicationPipelineFactoryTestRunner` fue integrado temporalmente en
el diagnóstico técnico de `MainWindow`.

La integración permite ejecutar la comprobación desde la interfaz actual y
mostrar:

- los mensajes de error, si alguna condición falla;
- el resultado general de la prueba;
- el resumen consolidado del runner.

La prueba se ejecuta después de las comprobaciones estructurales de
`MetadataVerificationStage` y antes de seleccionar el diagnóstico aislado
correspondiente al formato del archivo.

Esta integración es diagnóstica y no convierte a `MainWindow` en responsable de
la composición real del pipeline.

## Verificación complementaria

Después de integrar el runner de composición se ejecutó nuevamente el
diagnóstico técnico con un archivo MP3.

Se comprobó que:

- las pruebas estructurales de `MetadataVerificationStage` continuaron
  superándose;
- las ocho comprobaciones de la fábrica fueron aprobadas;
- el diagnóstico continuó normalmente después del nuevo runner;
- la inspección aislada MP3 terminó correctamente;
- el archivo musical original permaneció intacto;
- el respaldo aislado fue verificado;
- la carátula incrustada fue preservada.

## Alcance de la validación

La prueba realizada demuestra que el pipeline predeterminado está correctamente
construido y configurado.

Todavía no demuestra una ejecución integral en la que las cuatro etapas operen
conjuntamente sobre una copia aislada de un archivo real.

Esa comprobación corresponderá a un milestone posterior dedicado a la ejecución
end-to-end del pipeline.

## Decisión arquitectónica

La composición predeterminada queda encapsulada en una fábrica independiente.

`MainWindow` y los futuros consumidores no necesitarán conocer:

- qué implementaciones concretas utilizan las etapas;
- cómo se construyen sus dependencias;
- qué orden de ejecución tiene cada etapa;
- qué opciones seguras necesita el ejecutor.

Esta decisión proporciona un único punto de evolución para la composición y
evita configuraciones diferentes entre consumidores.

La fábrica crea objetos nuevos en cada invocación y conserva separadas las
responsabilidades de composición, ejecución, estado compartido y operación
funcional.
