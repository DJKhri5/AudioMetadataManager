# Milestone 13.25

## Ejecución coordinada de cambios aprobados sobre una copia aislada

## Objetivo

Conectar las propuestas aprobadas del Modo Simulación con el coordinador productivo de aplicación de metadatos, ejecutando el pipeline completo exclusivamente sobre una copia temporal aislada.

El objetivo principal de este milestone es validar el flujo real iniciado por el usuario desde la interfaz sin entregar todavía el archivo original al motor de escritura.

## Alcance

Este milestone incorpora:

* un resultado consolidado para ejecuciones aisladas;
* un ejecutor que coordina aislamiento, aplicación, verificación y limpieza;
* pruebas integrales del nuevo ejecutor;
* integración temporal de dichas pruebas en Diagnóstico técnico;
* conexión del botón `Respaldar y aplicar cambios` con el ejecutor aislado;
* creación de una solicitud técnica desde el plan aprobado;
* ejecución del pipeline productivo completo de cinco etapas;
* comprobación de que el archivo original permanece intacto;
* confirmación visual y auditable del resultado;
* limpieza automática del entorno temporal;
* corrección del ciclo de vida del plan activo al cambiar o escanear bibliotecas.

## Resultado consolidado de ejecución aislada

Se incorporó:

```csharp
MetadataApplicationIsolatedExecutionResult
```

Este modelo reúne en un único resultado:

* el contexto de aislamiento;
* el resultado completo del pipeline;
* la verificación posterior del entorno aislado;
* el resultado de la limpieza temporal;
* cualquier mensaje de error capturado.

El resultado expone comprobaciones derivadas para determinar si:

* el entorno aislado fue preparado;
* el pipeline terminó correctamente;
* el archivo original permaneció intacto;
* la copia temporal fue modificada;
* el respaldo inicial fue preservado;
* la limpieza temporal se completó;
* la ejecución completa fue satisfactoria.

## Criterio de éxito

Una ejecución aislada se considera correcta solamente cuando se cumplen todas estas condiciones:

```text
Sin error capturado
    + entorno aislado preparado
    + pipeline completado
    + archivo original intacto
    + copia temporal modificada
    + respaldo inicial preservado
    + entorno temporal eliminado
```

El resultado no puede considerarse exitoso si falta cualquiera de estas comprobaciones.

## Ejecutor aislado coordinado

Se incorporó:

```csharp
MetadataApplicationIsolatedExecutor
```

Este servicio coordina el flujo completo:

```text
Solicitud aprobada
    → creación del entorno temporal
    → creación de una copia de trabajo
    → transformación de la solicitud
    → ejecución del coordinador productivo
    → verificación de aislamiento
    → eliminación del entorno temporal
    → resultado consolidado
```

El servicio utiliza:

```text
FileIsolationTestHarness
MetadataApplyRequestIsolationFactory
IMetadataApplicationCoordinator
```

## Preparación del entorno aislado

Antes de ejecutar el pipeline, el servicio crea un entorno temporal mediante:

```csharp
FileIsolationTestHarness.CreateAsync(...)
```

El entorno contiene:

* la ruta del archivo original;
* una copia temporal de trabajo;
* un respaldo inicial independiente;
* hashes SHA-256 previos a la escritura;
* información necesaria para verificar posteriormente el aislamiento.

La copia de trabajo es el único archivo que puede entregarse al pipeline.

## Transformación de la solicitud

La solicitud creada desde el Modo Simulación conserva:

* identificador de solicitud;
* identificador del plan;
* fecha de creación;
* cambios aprobados;
* requisito de respaldo;
* requisito de verificación posterior.

Antes de ejecutar el coordinador, la solicitud se transforma mediante:

```csharp
MetadataApplyRequestIsolationFactory.Create(...)
```

Esta operación sustituye únicamente:

```text
FilePath
FileName
```

Los nuevos valores corresponden a la copia temporal.

## Ejecución del coordinador

La solicitud aislada se entrega a:

```csharp
IMetadataApplicationCoordinator.ExecuteAsync(...)
```

El coordinador ejecuta la composición predeterminada de cinco etapas:

```text
1. Validación
2. Respaldo
3. Escritura
4. Verificación posterior
5. Finalización
```

El archivo original nunca se entrega al coordinador ni al escritor.

## Verificación posterior

Después del pipeline se ejecuta:

```csharp
FileIsolationTestHarness.VerifyAsync(...)
```

La verificación compara los hashes y comprueba que:

* el archivo original conserve exactamente su estado inicial;
* la copia temporal haya recibido cambios reales;
* el respaldo inicial coincida con el estado previo de la copia;
* la escritura no haya escapado del entorno aislado.

## Limpieza del entorno

La limpieza se ejecuta desde el bloque `finally`.

Esto permite intentar la eliminación del entorno temporal incluso cuando:

* el pipeline falla;
* se produce una excepción;
* la operación es cancelada;
* la verificación no puede completarse.

El resultado registra explícitamente si la limpieza fue correcta.

## Conexión con la interfaz

El evento:

```csharp
ApplyChangesButton_Click
```

se convirtió en un evento asíncrono.

Después de la confirmación del usuario, el flujo ahora:

1. deshabilita temporalmente el botón;
2. crea la solicitud desde el plan aprobado;
3. prepara una copia aislada;
4. ejecuta el coordinador productivo;
5. muestra las comprobaciones en el registro;
6. informa el resultado mediante un cuadro de diálogo;
7. restaura el estado del botón.

## Creación de la solicitud aprobada

La solicitud se construye mediante:

```csharp
MetadataApplyRequestFactory.Create(
    _currentSimulationPlan)
```

La fábrica traslada únicamente los cambios aprobados desde el plan activo.

Después, `MetadataApplicationIsolatedExecutor` transforma la solicitud para que el pipeline trabaje con la copia temporal.

## Confirmación de seguridad

El cuadro de confirmación informa explícitamente que:

* los cambios serán ejecutados sobre una copia temporal;
* el archivo original permanecerá protegido;
* el original no será entregado al escritor;
* la copia y su respaldo serán eliminados después de las verificaciones.

La opción predeterminada continúa siendo:

```text
No
```

## Bloqueo durante la ejecución

Después de confirmar, el botón queda deshabilitado mientras la operación está activa.

Esto evita:

* ejecuciones simultáneas;
* pulsaciones duplicadas;
* múltiples pipelines sobre el mismo plan;
* resultados mezclados en el registro.

Al finalizar, el estado del botón vuelve a calcularse mediante:

```csharp
UpdateApplyChangesButtonState()
```

## Mensaje final al usuario

Cuando la operación termina correctamente, la aplicación informa:

```text
La ejecución sobre la copia temporal terminó correctamente.

El archivo original permaneció intacto.

Todavía no se han aplicado cambios al archivo original.
```

Este mensaje diferencia claramente una prueba productiva aislada de una aplicación definitiva sobre el archivo original.

## Manejo de fallos

Cuando la ejecución no supera todas las comprobaciones:

* se registra el error;
* se conserva el resultado parcial;
* se intenta limpiar el entorno;
* se muestra un mensaje de advertencia;
* no se declara éxito;
* no se asume que el archivo original fue modificado.

Las excepciones no controladas por las dependencias se capturan en `MainWindow` y se muestran en el registro.

## Correcciones del ciclo de vida del plan

Durante la integración se detectó una llamada duplicada a:

```csharp
SetCurrentSimulationPlan(
    null)
```

en `ScanButton_Click`.

La llamada duplicada fue eliminada.

También se agregó la limpieza del plan activo a `BrowseButton_Click`.

Con esto se evita que un plan generado para una biblioteca anterior permanezca disponible después de seleccionar otra carpeta.

## Garantía actual

El sistema ya puede ejecutar desde la interfaz el pipeline productivo completo con cambios aprobados, pero únicamente sobre una copia temporal aislada.

El archivo original permanece fuera del proceso de escritura.

## Limitaciones actuales

* Los cambios todavía no se aplican al archivo original.
* La copia modificada se elimina después de la verificación.
* El usuario todavía no puede conservar la copia resultante.
* No existe aún una segunda confirmación para promover la copia verificada al archivo original.
* No se procesa todavía un lote completo de archivos aprobados.
* No existe todavía restauración productiva desde el respaldo.
* La integración diagnóstica temporal continúa activa.
* El estado visual del plan no se modifica después de una ejecución aislada satisfactoria.

## Próximo paso previsto

El siguiente milestone deberá diseñar la transición segura desde una copia aislada verificada hacia una aplicación definitiva.

Antes de reemplazar o modificar el archivo original será necesario definir:

* respaldo productivo persistente;
* ubicación configurable del respaldo;
* segunda confirmación explícita;
* estrategia de reemplazo atómico;
* validación del archivo resultante;
* procedimiento de reversión;
* auditoría del cambio definitivo;
* soporte inicial para operación individual antes del procesamiento por lotes.
