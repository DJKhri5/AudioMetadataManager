# 13.29 - Actualización automática de la simulación después de aplicar cambios

## Objetivo

Actualizar automáticamente la interfaz y reconstruir el plan de simulación después de completar correctamente una aplicación productiva de metadatos.

El flujo debe reflejar inmediatamente el estado real del archivo modificado, sin exigir que el usuario vuelva a presionar manualmente:

```text
Analizar archivo
```

Después de una promoción productiva correcta, la aplicación debe:

1. volver a leer el archivo original desde el disco;
2. actualizar su fila en la biblioteca;
3. mantener seleccionado el archivo aplicado;
4. ejecutar nuevamente el análisis individual;
5. reconstruir el plan de simulación;
6. mostrar los valores persistidos como valores actuales;
7. eliminar de la interfaz el cambio que acaba de aplicarse cuando ya no sea necesario.

---

## Situación anterior

El Milestone 13.28 conectó el botón:

```text
Respaldar y aplicar cambios
```

con el flujo productivo completo:

```text
PrepareAsync
→ segunda confirmación
→ CompleteAsync
→ promoción o rechazo
→ limpieza controlada
```

Después de una promoción correcta, la interfaz llamaba a:

```text
RefreshAppliedAudioFile
```

Este método volvía a leer el archivo desde el disco y reemplazaba el elemento correspondiente dentro de la colección:

```text
audioFiles
```

La fila principal mostraba correctamente los metadatos nuevos.

Sin embargo, el panel de simulación continuaba mostrando el plan anterior porque:

```text
_currentSimulationPlan
```

todavía correspondía al análisis realizado antes de aplicar los cambios.

El método de actualización terminaba limpiando o conservando un estado de simulación que no había sido reconstruido desde el archivo recién modificado.

Como consecuencia, el usuario debía presionar nuevamente:

```text
Analizar archivo
```

para comprobar que el cambio había sido persistido.

---

## Comportamiento observado

Durante las primeras pruebas se identificaron dos comportamientos incorrectos.

### Panel de simulación vacío

Después de la segunda confirmación y de una promoción correcta, el panel de simulación quedaba sin campos visibles.

Era necesario presionar nuevamente:

```text
Analizar archivo
```

para reconstruir la información.

### Plan anterior conservado

Después de una modificación posterior, la interfaz mantenía visible el plan de simulación anterior.

El campo aplicado seguía apareciendo como:

```text
Valor actual: valor anterior
Valor propuesto: valor aprobado
Estado de revisión: Aprobado por el usuario
```

aunque el archivo real ya contenía el valor nuevo.

Al analizar nuevamente el archivo, la interfaz mostraba correctamente:

```text
Valor actual: valor aplicado
Valor propuesto: valor aplicado
Decisión: No requiere cambios
Estado de revisión: Sin cambios
```

Esto confirmó que la escritura productiva era correcta y que el problema estaba limitado a la actualización posterior de la interfaz.

---

## Origen del problema

La actualización posterior estaba dividida en dos operaciones independientes.

La primera operación:

```text
RefreshAppliedAudioFile
```

actualizaba solamente:

- la colección de archivos;
- la fila seleccionada;
- los metadatos visibles del archivo;
- la selección dentro del `DataGrid`.

La segunda operación, correspondiente al análisis individual, continuaba dependiendo de una acción manual del usuario.

Por lo tanto, actualizar la fila no era suficiente para regenerar:

```text
SimulationPlanViewModel
```

El plan de simulación debía construirse nuevamente ejecutando el mismo flujo utilizado por el botón:

```text
Analizar archivo
```

pero sin repetir toda la información técnica en el Registro de actividad.

---

## Unificación del análisis individual

La lógica del botón de análisis fue extraída a un método reutilizable:

```csharp
private async Task AnalyzeSelectedFileAsync(
    FileAnalysisInvocation invocation)
```

El controlador visual quedó reducido a:

```csharp
private async void AnalyzeSelectedFileButton_Click(
    object sender,
    RoutedEventArgs e)
{
    await AnalyzeSelectedFileAsync(
        FileAnalysisInvocation.UserRequested);
}
```

Esto permite reutilizar el mismo análisis desde dos orígenes:

```text
Acción manual del usuario
Actualización automática posterior a la aplicación
```

La reconstrucción utiliza el mismo pipeline, los mismos motores y las mismas fábricas que el análisis normal.

No se creó una segunda implementación paralela del análisis.

---

## Identificación del origen del análisis

Se agregó la enumeración interna:

```csharp
private enum FileAnalysisInvocation
{
    UserRequested,
    PostApplicationRefresh
}
```

### UserRequested

Representa un análisis iniciado explícitamente mediante:

```text
Analizar archivo
```

En este modo, el Registro de actividad conserva todos los diagnósticos detallados.

### PostApplicationRefresh

Representa un análisis ejecutado automáticamente después de una promoción productiva correcta.

En este modo:

- se reconstruye completamente el plan;
- se vuelven a calcular las propuestas;
- se actualiza la interfaz;
- se evita repetir en el registro todos los informes técnicos extensos;
- se agrega solamente un mensaje compacto de confirmación.

---

## Detección del modo posterior a la aplicación

Dentro del método compartido se determina el modo mediante:

```csharp
bool isPostApplicationRefresh =
    invocation ==
    FileAnalysisInvocation.PostApplicationRefresh;
```

Esta variable controla únicamente la presentación de los diagnósticos.

No modifica:

- las búsquedas externas;
- el ranking de candidatos;
- el consenso;
- el plan de modificaciones;
- las reglas de confianza;
- las decisiones de aplicación;
- el contenido final del plan de simulación.

El análisis funcional sigue siendo completo.

---

## Supresión controlada de diagnósticos repetidos

Durante un análisis solicitado por el usuario se muestran informes como:

```text
Diagnóstico de MetadataSearchPipeline
Ranking de candidatos externos
Diagnóstico de Metadata Consensus
Diagnóstico del plan de modificaciones
Diagnóstico de MetadataComparisonEngine
Diagnóstico de MetadataConfidenceEngine
```

Después de aplicar un cambio, esos informes ya fueron mostrados durante el análisis original.

Repetirlos automáticamente generaba una gran cantidad de texto duplicado en:

```text
Registro de actividad
```

Por esta razón, los bloques de diagnóstico visual se condicionaron mediante:

```csharp
if (!isPostApplicationRefresh)
{
    // Agregar informe al registro.
}
```

Esta condición se aplicó a los informes de:

- búsqueda de fuentes;
- ranking de candidatos;
- consenso;
- comparación;
- confianza;
- plan de modificaciones.

Los motores continúan ejecutándose normalmente.

Solamente se evita volver a mostrar sus informes extensos durante la actualización automática.

---

## Actualización del archivo aplicado

Después de una promoción correcta se continúa ejecutando:

```csharp
bool interfaceWasRefreshed =
    RefreshAppliedAudioFile(
        request.FilePath);
```

El método vuelve a leer el archivo mediante el escáner real y actualiza:

```text
audioFiles
AudioFilesDataGrid.ItemsSource
AudioFilesDataGrid.SelectedItem
AudioFilesDataGrid.ScrollIntoView
```

La fila aplicada queda seleccionada después del reemplazo.

El registro conserva:

```text
La fila aplicada fue actualizada desde el archivo real.
```

y:

```text
Interfaz actualizada desde el archivo aplicado: Sí
```

---

## Reconstrucción automática del plan

Cuando la actualización de la fila termina correctamente, se ejecuta:

```csharp
if (interfaceWasRefreshed)
{
    await AnalyzeSelectedFileAsync(
        FileAnalysisInvocation.PostApplicationRefresh);

    AppendLog(
        "El plan de simulación fue reconstruido desde " +
        "el archivo aplicado.");
}
```

Este bloque se ejecuta únicamente cuando:

```text
WasSuccessfullyPromoted = true
```

y la fila correspondiente pudo actualizarse desde el archivo real.

La reconstrucción ocurre antes de mostrar el mensaje final:

```text
Cambios aplicados
```

De esta manera, cuando el usuario cierra el cuadro de confirmación, la interfaz ya representa el estado actualizado.

---

## Secuencia final del camino Approved

El camino productivo aprobado queda compuesto por:

```text
Plan de simulación con cambios aprobados
→ PrepareAsync
→ copia aislada
→ pipeline completo
→ verificación de la copia
→ segunda confirmación
→ Approved
→ respaldo productivo
→ sustitución controlada
→ verificación del destino
→ limpieza del entorno aislado
→ lectura del archivo original
→ actualización de la fila
→ análisis individual automático
→ reconstrucción del plan
→ mensaje de cambios aplicados
```

La reconstrucción del plan ocurre solamente después de comprobar que la promoción fue exitosa.

---

## Comportamiento después de aplicar un campo

Durante la prueba se aprobó una modificación de género.

Antes de aplicar:

```text
Valor actual: valor anterior
Valor propuesto: Electronic
Decisión: Revisión manual requerida
Estado de revisión: Aprobado por el usuario
```

Después de la promoción productiva, la aplicación volvió a analizar automáticamente el archivo.

La interfaz mostró:

```text
Valor actual: Electronic
Valor propuesto: Electronic
Decisión: No requiere cambios
Estado de revisión: Sin cambios
```

El cambio anterior dejó de presentarse como pendiente porque el valor solicitado ya estaba persistido en el archivo.

---

## Conservación del plan para otros campos

La reconstrucción no elimina las demás propuestas del archivo.

Después de aplicar un campo:

- el campo aplicado pasa a `No requiere cambios`;
- las propuestas no aplicadas continúan disponibles;
- los campos pendientes mantienen su estado de revisión;
- las casillas no aprobadas permanecen sin seleccionar;
- el usuario puede continuar revisando otros campos.

Por ejemplo, si se aplica solamente:

```text
Género
```

una propuesta pendiente de:

```text
Sello
```

continúa disponible para una operación posterior.

---

## Validación del camino cancelado

También se comprobó el camino en el que el usuario cancela la ejecución.

El registro mostró:

```text
La ejecución aislada fue cancelada por el usuario.
```

En ese caso:

- no se promueve ninguna copia;
- no se modifica el archivo original;
- no se reconstruye automáticamente el plan;
- la interfaz mantiene el análisis existente;
- el usuario puede continuar revisando el archivo.

La actualización posterior se reserva exclusivamente para promociones productivas completadas.

---

## Validación del camino aprobado

La prueba funcional aprobada confirmó:

```text
Entorno aislado preparado: Sí
Pipeline completado: Sí
Archivo original intacto durante la preparación: Sí
Copia temporal modificada: Sí
Respaldo inicial preservado: Sí
Copia disponible para segunda confirmación: Sí
Promoción aprobada: Sí
Respaldo productivo creado: Sí
Respaldo productivo verificado: Sí
Sustitución controlada ejecutada: Sí
Destino promovido verificado: Sí
Entorno aislado eliminado: Sí
Archivo original en estado seguro: Sí
Interfaz actualizada desde el archivo aplicado: Sí
```

Después de la promoción, el análisis automático se ejecutó correctamente.

El registro terminó con:

```text
El plan de simulación fue reconstruido desde el archivo aplicado.
```

No fue necesario volver a presionar:

```text
Analizar archivo
```

---

## Evidencia en el Registro de actividad

El flujo completo dejó evidencia de:

```text
La fila aplicada fue actualizada desde el archivo real.
Interfaz actualizada desde el archivo aplicado: Sí
El plan de simulación fue reconstruido desde el archivo aplicado.
```

El mensaje de reconstrucción aparece después de la finalización productiva.

Esto permite distinguir:

```text
Actualización de la fila
```

de:

```text
Reconstrucción completa del plan
```

Ambas operaciones son necesarias para mantener la interfaz sincronizada.

---

## Seguridad

La actualización automática no modifica directamente el archivo.

El único componente autorizado para promover la copia continúa siendo:

```text
MetadataProductiveApplicationCoordinator
```

El análisis posterior:

- se ejecuta después de la promoción;
- abre el archivo en modo de lectura;
- reconstruye el estado visual;
- no escribe etiquetas;
- no reutiliza la copia temporal;
- no modifica el respaldo productivo;
- no altera el resultado de la promoción.

La separación de responsabilidades permanece intacta:

```text
Coordinador productivo
→ modifica el archivo de forma controlada
```

```text
Análisis posterior
→ vuelve a leer y representa el resultado
```

---

## Resultado final

El Milestone 13.29 deja funcional la sincronización automática posterior a una aplicación productiva.

La aplicación ahora:

- vuelve a leer el archivo promovido;
- actualiza la fila correspondiente;
- conserva la selección del archivo;
- reutiliza el flujo real de análisis individual;
- reconstruye automáticamente el plan de simulación;
- evita duplicar informes técnicos extensos;
- muestra inmediatamente los valores persistidos;
- convierte el campo aplicado en `No requiere cambios`;
- conserva las demás propuestas pendientes;
- elimina la necesidad de volver a pulsar `Analizar archivo`.

Resultado validado:

```text
Promoción productiva correcta
→ interfaz actualizada
→ plan reconstruido automáticamente
→ cambio persistido visible
→ operación pendiente eliminada
```

La prueba funcional terminó correctamente y el archivo aplicado quedó representado en la interfaz con su estado real.
