# 13.30 - Coordinación productiva de metadatos por lote

## Objetivo

Incorporar una capa de coordinación productiva capaz de procesar múltiples solicitudes de aplicación de metadatos como un lote secuencial, auditable y seguro.

El milestone amplía el flujo productivo individual existente:

```text
PrepareAsync
→ decisión de promoción
→ CompleteAsync
```

para permitir:

```text
Solicitud 1
→ Solicitud 2
→ Solicitud 3
→ ...
```

sin duplicar la lógica de aplicación individual.

La coordinación por lote debe reutilizar:

```text
IMetadataProductiveApplicationCoordinator
```

como única autoridad para preparar, promover, rechazar, limpiar y verificar cada aplicación productiva individual.

---

## Situación anterior

Hasta el Milestone 13.29 la aplicación disponía de un flujo productivo completo para un único archivo.

El flujo individual ya soportaba:

```text
plan aprobado
→ solicitud productiva
→ preparación aislada
→ pipeline completo
→ copia verificada
→ segunda confirmación
→ Approved o Declined
→ promoción o rechazo
→ limpieza
→ actualización de la interfaz
→ reconstrucción del plan
```

Este diseño protegía correctamente cada archivo, pero no existía una abstracción para ejecutar varias solicitudes productivas como una operación coordinada.

Cualquier futura aplicación masiva habría necesitado:

- repetir manualmente el coordinador individual;
- implementar sus propias reglas de cancelación;
- decidir cómo detenerse después de un fallo;
- construir manualmente resultados agregados;
- registrar de forma independiente las solicitudes no ejecutadas;
- definir qué hacer cuando una solicitud anterior ya fue promovida.

El objetivo del milestone es centralizar esas reglas antes de conectar el procesamiento productivo masivo a la interfaz principal.

---

## Nuevos modelos de lote

Se incorporó:

```text
MetadataApplyBatchRequest
```

como representación de una solicitud productiva formada por múltiples `MetadataApplyRequest`.

El modelo permite consolidar:

- identidad del lote;
- fecha de creación;
- solicitudes originales;
- solicitudes estructuralmente válidas;
- cantidad de solicitudes válidas;
- cantidad total de cambios utilizables;
- detección de rutas duplicadas;
- validez estructural global.

Las solicitudes inválidas pueden ser identificadas sin delegar una operación insegura al coordinador productivo.

Las rutas duplicadas invalidan el lote para impedir que dos solicitudes del mismo batch intenten modificar el mismo archivo.

---

## Resultado productivo por lote

Se incorporó:

```text
MetadataApplyBatchResult
```

para consolidar el resultado global de la operación.

El resultado registra:

- `BatchId`;
- inicio de la ejecución;
- fin de la ejecución;
- resultados productivos individuales;
- mensajes auditables;
- duración global;
- cantidad de resultados procesados;
- cantidad de resultados satisfactorios;
- cantidad de resultados no satisfactorios;
- estado global del lote.

El modelo permite representar correctamente un lote parcialmente procesado.

Por ejemplo:

```text
Solicitud 1 → completada
Solicitud 2 → fallida
Solicitud 3 → no ejecutada
```

sin perder el resultado ya producido por la primera solicitud.

---

## Contrato del coordinador productivo por lote

Se incorporó:

```text
IMetadataProductiveApplicationBatchCoordinator
```

y su implementación:

```text
MetadataProductiveApplicationBatchCoordinator
```

El coordinador recibe:

```text
MetadataApplyBatchRequest
MetadataPromotionDecision
CancellationToken
```

y delega cada solicitud válida al coordinador productivo individual.

La ejecución es deliberadamente secuencial:

```text
request 1
→ PrepareAsync
→ CompleteAsync

request 2
→ PrepareAsync
→ CompleteAsync

request 3
→ PrepareAsync
→ CompleteAsync
```

No se realizan promociones productivas concurrentes.

Esta decisión mantiene:

- orden determinista;
- trazabilidad clara;
- menor superficie de riesgo;
- compatibilidad con el sistema de backups;
- compatibilidad con la protección de preparaciones individuales;
- comportamiento fail-fast sencillo de auditar.

---

## Decisiones de promoción permitidas

La ejecución batch solamente admite:

```text
Approved
Declined
```

Estados como:

```text
Pending
NotRequested
Unavailable
```

son rechazados antes de ejecutar el coordinador individual.

Esto evita iniciar un lote sin una decisión explícita y definitiva.

La decisión aprobada o rechazada se reenvía a cada llamada individual a:

```text
CompleteAsync
```

---

## Procesamiento Declined

Un lote con decisión:

```text
Declined
```

continúa procesando cada solicitud válida mediante:

```text
PrepareAsync
→ CompleteAsync(... Declined)
```

El coordinador individual conserva la responsabilidad de:

- no promover el archivo original;
- eliminar el entorno aislado;
- dejar el original intacto;
- devolver un resultado controlado.

El coordinador batch solamente agrega esos resultados.

---

## Procesamiento Approved

Un lote con decisión:

```text
Approved
```

reenvía `Approved` a cada solicitud individual.

Las pruebas controladas verificaron un lote de tres solicitudes:

```text
Solicitud 1 → Approved
Solicitud 2 → Approved
Solicitud 3 → Approved
```

Todas recibieron la decisión correcta.

El coordinador batch no implementa una segunda lógica de promoción.

Cada archivo continúa utilizando el flujo individual existente:

```text
backup productivo
→ preparación de sustitución
→ reemplazo
→ verificación
→ rollback individual si corresponde
→ limpieza
```

---

## Política fail-fast

La política definida para esta fase es:

```text
primer fallo
→ detener inmediatamente el lote
```

No se inicia ninguna solicitud posterior.

Ejemplo:

```text
Solicitud 1
PrepareAsync → correcto
CompleteAsync → correcto

Solicitud 2
PrepareAsync → fallo

Solicitud 3
→ no iniciada
```

La prueba confirmó:

```text
PrepareCallCount = 2
CompleteCallCount = 1
```

También se validó un fallo durante la finalización:

```text
Solicitud 1
PrepareAsync → correcto
CompleteAsync → correcto

Solicitud 2
PrepareAsync → correcto
CompleteAsync → fallo

Solicitud 3
→ no iniciada
```

con:

```text
PrepareCallCount = 2
CompleteCallCount = 2
```

---

## Excepciones inesperadas

El coordinador batch protege la ejecución contra excepciones inesperadas del coordinador individual.

Cuando una llamada individual lanza una excepción distinta de cancelación:

```text
PrepareAsync
```

o:

```text
CompleteAsync
```

el lote:

1. captura la excepción;
2. construye un `MetadataProductiveApplicationResult` fallido;
3. conserva el mensaje en `ErrorMessage`;
4. agrega evidencia auditable;
5. incorpora el resultado al batch;
6. detiene inmediatamente las solicitudes posteriores.

Por lo tanto, el fallo parcial continúa representado dentro de:

```text
MetadataApplyBatchResult
```

en lugar de perderse únicamente como una excepción externa.

---

## Fallos controlados devueltos por el coordinador individual

El coordinador individual real captura numerosos fallos técnicos y los representa mediante:

```text
MetadataProductiveApplicationResult.ErrorMessage
```

Por esta razón, el coordinador batch no puede limitarse a detectar excepciones.

Después de `PrepareAsync` se inspecciona:

```text
preparedResult.ErrorMessage
```

y después de `CompleteAsync`:

```text
completedResult.ErrorMessage
```

Cuando alguno contiene un fallo:

```text
resultado fallido
→ conservar resultado
→ registrar mensaje
→ detener lote
```

Se validaron de forma independiente:

```text
fallo devuelto por PrepareAsync
fallo devuelto por CompleteAsync
```

Ambos detuvieron correctamente el lote.

---

## Preservación del fallo parcial

La ejecución por lote conserva todos los resultados que ya fueron producidos antes del fallo.

Ejemplo:

```text
Solicitud 1 → resultado correcto
Solicitud 2 → resultado fallido
Solicitud 3 → no ejecutada
```

El resultado batch contiene:

```text
Results.Count = 2
```

El primer elemento permanece intacto.

El segundo elemento conserva el error que detuvo la operación.

Esto permite auditar exactamente hasta dónde avanzó el lote.

---

## Solicitudes no ejecutadas

Cuando el lote se detiene antes de procesar todas sus solicitudes se calcula la cantidad restante.

El registro incorpora un mensaje equivalente a:

```text
1 solicitud(es) no fueron ejecutadas porque el lote se detuvo anticipadamente.
```

Esto permite distinguir entre:

```text
solicitud fallida
```

y:

```text
solicitud nunca iniciada
```

La diferencia es importante para futuros mecanismos de reintento, reanudación y revisión manual.

---

## Cancelación previa

El coordinador respeta un `CancellationToken` cancelado antes de iniciar la ejecución.

En ese caso:

```text
ninguna solicitud se prepara
ninguna solicitud se finaliza
```

y se propaga:

```text
OperationCanceledException
```

La cancelación no se transforma en un error técnico normal.

---

## Cancelación durante un lote iniciado

También se validó la cancelación después de completar correctamente la primera solicitud.

Secuencia:

```text
Solicitud 1
PrepareAsync → correcto
CompleteAsync → correcto

→ CancellationToken cancelado

Solicitud 2
→ no iniciada
```

La prueba confirmó:

```text
PrepareCallCount = 1
CompleteCallCount = 1
```

y la ejecución terminó mediante:

```text
OperationCanceledException
```

Esto preserva la semántica normal de cancelación de .NET y evita continuar el lote después de una solicitud explícita de detener la operación.

---

## Política de rollback del lote

El batch no implementa un rollback transaccional global.

Si una solicitud ya terminó correctamente y una solicitud posterior falla:

```text
Solicitud 1 → completada
Solicitud 2 → fallo
```

el coordinador batch:

```text
conserva Solicitud 1
detiene Solicitud 2
no inicia Solicitud 3
```

pero no intenta revertir automáticamente `Solicitud 1`.

Esta decisión es intencional.

El rollback de seguridad continúa perteneciendo a:

```text
MetadataApplicationPromotionService
```

para cada archivo individual.

Ese servicio ya dispone de:

```text
backup productivo
verificación de reemplazo
rollback automático
verificación del destino restaurado
```

Por lo tanto:

```text
rollback individual
```

protege la integridad de cada archivo, mientras que:

```text
fail-fast batch
```

controla hasta dónde continúa una operación masiva.

Una futura transacción global multiarchivo, si se considerara necesaria, deberá diseñarse como un milestone independiente.

---

## Fallo durante un lote Approved

También se validó:

```text
Solicitud 1 → Approved correcto
Solicitud 2 → fallo durante CompleteAsync
Solicitud 3 → no iniciada
```

El resultado de la primera solicitud permaneció conservado con:

```text
PromotionDecision = Approved
ErrorMessage vacío
```

y el segundo resultado conservó el error simulado.

Esto confirma la política:

```text
no rollback global automático
```

sin alterar las garantías de seguridad individuales.

## Coordinador controlado para pruebas

Se extendió:

```text
RecordingProductiveApplicationCoordinator
```

para simular de forma determinista:

- excepciones en `PrepareAsync`;
- excepciones en `CompleteAsync`;
- resultados fallidos devueltos desde `PrepareAsync`;
- resultados fallidos devueltos desde `CompleteAsync`;
- registro de decisiones de promoción;
- cancelación después de una llamada concreta;
- conteo exacto de preparaciones;
- conteo exacto de finalizaciones.

Esto permite comprobar las reglas batch sin modificar archivos reales.

## Arquitectura resultante

La cadena productiva queda ahora organizada en dos niveles.

### Nivel individual

```text
MetadataProductiveApplicationCoordinator

PrepareAsync
→ aislamiento
→ pipeline
→ copia verificada

CompleteAsync
→ Declined
   o
→ Approved
→ promoción
→ rollback individual cuando corresponda
→ limpieza
```

### Nivel batch

```text
MetadataProductiveApplicationBatchCoordinator

MetadataApplyBatchRequest
→ validar decisión
→ solicitudes válidas
→ ejecución secuencial
→ coordinador individual
→ agregar resultado
→ detectar fallo
→ fail-fast
→ registrar solicitudes restantes
→ MetadataApplyBatchResult
```

El coordinador batch no conoce detalles de:

- TagLibSharp;
- MP3;
- FLAC;
- backups internos;
- staging files;
- hashes;
- escritura de metadatos;
- rollback físico.

Todas esas responsabilidades permanecen encapsuladas en los servicios individuales existentes.

---

## Decisiones arquitectónicas

### Reutilizar el coordinador individual

No se creó una segunda implementación productiva para lotes.

El batch depende exclusivamente de:

```text
IMetadataProductiveApplicationCoordinator
```

### Ejecución secuencial

No se ejecutan solicitudes productivas en paralelo.

### Fail-fast

El primer fallo detiene nuevas solicitudes.

### Fallos auditables

Las excepciones inesperadas se convierten en resultados individuales fallidos dentro del batch.

### Cancelación real

`OperationCanceledException` continúa propagándose y no se convierte en un error técnico ordinario.

### Sin rollback global

Un fallo posterior no revierte automáticamente aplicaciones individuales ya completadas.

### Responsabilidades separadas

El batch coordina.

El coordinador individual protege cada archivo.

El servicio de promoción ejecuta reemplazo y rollback.

---

## Limitaciones actuales

Este milestone no conecta todavía la coordinación batch con una acción productiva masiva de la interfaz.

Tampoco incorpora todavía:

- barra de progreso de lote;
- pausa y reanudación;
- persistencia de ejecución batch;
- reintento de solicitudes fallidas;
- selección interactiva de archivos después de un fallo;
- rollback transaccional multiarchivo;
- procesamiento productivo paralelo.

Estas capacidades deberán evaluarse en milestones posteriores.
