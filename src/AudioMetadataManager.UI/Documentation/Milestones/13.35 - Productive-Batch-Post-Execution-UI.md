# Milestone 13.35 - Productive Batch Post-Execution UI

## Objetivo

Completar y estabilizar la experiencia de interfaz asociada a la ejecución productiva por lote después de integrar el workflow de dos fases del milestone anterior.

El objetivo principal de este milestone es asegurar que la interfaz:

- mantenga un estado productivo coherente antes, durante y después de la ejecución por lote;
- no permita ejecutar propuestas que el escritor productivo todavía no puede persistir de forma segura;
- muestre errores productivos reales y auditables cuando la preparación aislada falla;
- conserve la separación entre simulación y aplicación productiva;
- permita validar de extremo a extremo una promoción productiva real sin introducir regresiones en la infraestructura existente.

## Cambios realizados

### Estado productivo de la selección

Se reforzó `ProductiveBatchSelection` para representar de forma explícita si la selección actual está lista para una ejecución productiva.

La interfaz utiliza este estado para habilitar o deshabilitar las acciones de lote y evitar estados ambiguos cuando no existen solicitudes productivas válidas.

También se agregó cobertura automatizada para selecciones vacías y selecciones válidas listas para ejecución.

## Preparación y ejecución productiva por lote

`MainWindow` continúa utilizando el workflow productivo dedicado introducido en el milestone 13.34.

Durante este milestone se validó manualmente el flujo completo:

1. selección de una propuesta productivamente soportada;
2. creación del lote;
3. preparación aislada de la copia de trabajo;
4. backup y verificación;
5. escritura real de metadatos sobre la copia aislada;
6. verificación posterior a la escritura;
7. decisión global explícita del usuario;
8. promoción del archivo preparado;
9. finalización y limpieza;
10. actualización del estado visual posterior a la ejecución.

La prueba manual confirmó una ejecución productiva completa y correcta utilizando un cambio de `Genre` sobre un archivo MP3 real.

## Diagnóstico de fallos productivos

Durante la validación manual se detectó que los errores internos de una preparación aislada podían quedar ocultos detrás del mensaje genérico de lote:

`no produjo una copia verificada pendiente`.

Se mejoró la propagación de errores entre:

- `MetadataApplicationIsolatedExecutor`;
- `MetadataProductiveApplicationCoordinator`;
- `MetadataProductiveTwoPhaseBatchCoordinator`.

El diagnóstico conserva ahora información sobre:

- motivo de parada del pipeline;
- mensaje de error del pipeline;
- etapa que produjo el fallo;
- detalles internos disponibles;
- criterios de seguridad que impidieron conservar una copia promovible.

Esto permitió identificar de forma concreta un intento de escribir un campo que todavía no estaba soportado por el mapper productivo.

## Política centralizada de campos productivos

Se agregó `MetadataProductiveFieldSupport` como política única para determinar qué campos de metadatos pueden escribirse actualmente de forma productiva.

Los campos soportados en esta etapa son:

- `Artist`;
- `Title`;
- `Album`;
- `Genre`.

Los siguientes campos permanecen temporalmente fuera de la aplicación productiva:

- `Version`;
- `Label`.

Esta misma política se reutiliza tanto al construir `MetadataApplyRequest` como en el mapper TagLibSharp, evitando que ambas capas diverjan respecto de las capacidades reales del escritor.

## Protección de solicitudes productivas

`MetadataApplyRequestFactory` filtra ahora propuestas que no disponen de soporte productivo.

Esto evita que una propuesta visualmente aprobada para revisión termine convirtiéndose en una operación de escritura que el pipeline no puede ejecutar.

Se agregó cobertura para comprobar que:

- `Genre` se incluye correctamente;
- `Label` queda excluido;
- `Version` queda excluido;
- una combinación de campo soportado y no soportado conserva únicamente el campo productivamente válido.

## Experiencia de usuario en la simulación

`SimulationProposalViewModel` expone ahora de forma explícita:

- si el campo tiene soporte productivo;
- si puede seleccionarse para aplicación productiva;
- un estado legible de disponibilidad;
- una explicación para la interfaz.

Los campos sin soporte productivo:

- no pueden quedar seleccionados;
- no pueden formar parte de un lote productivo;
- muestran su estado como no disponible;
- mantienen deshabilitado su checkbox de aplicación.

La tabla de simulación incorpora además una columna de estado de aplicación productiva. Cuando el ancho visible no permite mostrarla completa, permanece accesible mediante el desplazamiento horizontal de la tabla.

## Seguridad

El milestone conserva las garantías existentes:

- la preparación productiva no modifica el archivo original;
- la promoción requiere una decisión explícita;
- las copias aisladas sólo se conservan cuando superan todas las verificaciones;
- los fallos del pipeline no producen promoción;
- los campos sin soporte de escritura no llegan al pipeline productivo;
- la limpieza y el rollback continúan delegados a la infraestructura productiva existente;
- la simulación sigue siendo independiente de la aplicación productiva.

## Pruebas automatizadas

Se amplió la cobertura automatizada para:

- disponibilidad productiva de campos;
- rechazo de `Label` y `Version` en solicitudes productivas;
- selección productiva válida e inválida;
- prevención de selección programática de campos sin soporte;
- conservación de las pruebas existentes de coordinación, preparación, promoción, rollback, pipeline y UI.

Al finalizar el milestone:

- la solución compila sin errores;
- se ejecutan 98 pruebas automatizadas;
- 98 pruebas finalizan correctamente;
- no existen pruebas fallidas.

## Validación manual

Se verificó manualmente que:

- una propuesta basada únicamente en `Label` no genera un lote productivo ejecutable;
- un campo soportado sí puede formar parte del lote;
- una ejecución real con `Genre` completa correctamente preparación, escritura, verificación y promoción;
- los checkboxes de campos no soportados permanecen deshabilitados;
- la interfaz no permite promover accidentalmente `Label` o `Version` mientras su escritura productiva no esté implementada.

## Resultado

La aplicación dispone ahora de una frontera clara entre propuestas de simulación y cambios realmente ejecutables por el pipeline productivo.

El flujo batch productivo quedó validado de extremo a extremo y la interfaz ya no puede enviar silenciosamente al escritor campos que todavía no sabe persistir.

Además, los fallos de preparación contienen información diagnóstica suficiente para localizar el componente responsable sin modificar a ciegas la coordinación de alto nivel.

El siguiente desarrollo puede continuar sobre una base productiva estable, con 98 pruebas automatizadas correctas y una política centralizada de capacidades de escritura.
