# 13.31 - Integración productiva batch en dos fases con la interfaz

## Objetivo

Conectar la coordinación productiva por lote incorporada en el Milestone 13.30 con la interfaz principal de Audio Metadata Manager, manteniendo las mismas garantías de seguridad que existen en el flujo productivo individual.

El milestone incorpora una selección productiva persistente de múltiples archivos y evoluciona la aplicación batch desde una ejecución secuencial con una decisión previamente conocida hacia un flujo productivo real de dos fases:

```text
selección de múltiples planes aprobados
→ construcción de MetadataApplyBatchRequest
→ primera confirmación
→ preparación aislada de todos los archivos
→ copias verificadas pendientes
→ segunda confirmación global
→ Approved o Declined
→ promoción o descarte
→ limpieza
→ actualización de la selección batch
→ relectura de archivos promovidos
→ reconstrucción del plan visible
```

La segunda confirmación ocurre únicamente después de que todas las copias del lote hayan sido preparadas y verificadas.

Ningún archivo original se modifica durante la primera fase.

---

## Situación anterior

El Milestone 13.30 introdujo:

```text
MetadataApplyBatchRequest
MetadataApplyBatchResult
IMetadataProductiveApplicationBatchCoordinator
MetadataProductiveApplicationBatchCoordinator
```

y permitió ejecutar múltiples solicitudes productivas de forma secuencial y auditable.

La ejecución era:

```text
Solicitud 1
→ PrepareAsync
→ CompleteAsync

Solicitud 2
→ PrepareAsync
→ CompleteAsync
```

utilizando una decisión `Approved` o `Declined` recibida antes de iniciar el lote.

Ese modelo era suficiente para establecer:

- coordinación secuencial;
- fail-fast;
- conservación de resultados parciales;
- cancelación;
- reporte de solicitudes no ejecutadas;
- reutilización del coordinador productivo individual.

Sin embargo, todavía no representaba correctamente la experiencia interactiva necesaria en la interfaz.

Para una aplicación productiva real era necesario:

```text
preparar todos los archivos
→ verificar todas las copias
→ detenerse
→ pedir confirmación global al usuario
→ decidir Approved o Declined
```

El Milestone 13.31 incorpora esa separación explícita.

---

## Selección productiva persistente por lote

Se incorporaron:

```text
ProductiveBatchSelection
ProductiveBatchSelectionItem
```

como estado persistente de la selección productiva mantenida por la interfaz.

La selección no depende de la selección visual simultánea del `DataGrid`.

El usuario puede trabajar secuencialmente:

```text
Archivo A
→ analizar
→ aprobar cambios
→ agregar al lote

Archivo B
→ analizar
→ aprobar cambios
→ agregar al mismo lote
```

aunque solamente una fila permanezca visualmente seleccionada.

La selección conserva por archivo:

- ruta;
- plan de simulación;
- cambios aprobados;
- cantidad de cambios utilizables.

Una ruta ya existente se reemplaza en lugar de duplicarse.

Si un plan deja de contener cambios aprobados, su entrada anterior se elimina automáticamente.

---

## Ciclo de vida de la selección batch

La selección productiva se limpia cuando:

```text
se selecciona una biblioteca diferente
```

o:

```text
se vuelve a escanear la biblioteca
```

Esto evita conservar planes pertenecientes a una biblioteca que ya no corresponde al contenido visible.

La interfaz muestra continuamente:

```text
Lote productivo: ningún archivo seleccionado
```

o:

```text
Lote productivo: N archivo(s) · M cambio(s)
```

según el estado actual.

---

## Fábrica de solicitudes batch desde la selección visual

Se incorporó:

```text
MetadataApplyBatchRequestFactory
```

para convertir la selección productiva persistente en:

```text
MetadataApplyBatchRequest
```

La fábrica reutiliza la información aprobada de los planes de simulación y produce solicitudes técnicas válidas sin duplicar la lógica de construcción de cada `MetadataApplyRequest`.

La solicitud batch conserva:

- identidad propia;
- solicitudes individuales;
- rutas;
- cambios aprobados;
- validación estructural;
- conteos de archivos y cambios.

---

## Integración visual

La interfaz principal incorpora un nuevo estado productivo batch y la acción:

```text
Revisar lote
```

separada de:

```text
Respaldar y aplicar cambios
```

El botón individual continúa perteneciendo exclusivamente al plan actualmente seleccionado.

El botón batch trabaja sobre:

```text
ProductiveBatchSelection
```

y solamente se habilita cuando existe al menos un archivo seleccionado para aplicación por lote.

Durante una operación batch:

```text
ReviewProductiveBatchButton.IsEnabled = false
ApplyChangesButton.IsEnabled = false
```

para impedir ejecuciones productivas superpuestas.

---

## Coordinación productiva batch en dos fases

Se incorporaron:

```text
IMetadataProductiveTwoPhaseBatchCoordinator
MetadataProductiveTwoPhaseBatchCoordinator
```

El nuevo coordinador reutiliza:

```text
IMetadataProductiveApplicationCoordinator
```

como única autoridad productiva individual.

La coordinación se divide en:

```text
PrepareAsync
CompleteAsync
```

pero ahora ambas operaciones pertenecen al lote completo.

---

## Primera fase: preparación global

La operación:

```text
PrepareAsync(MetadataApplyBatchRequest)
```

recorre secuencialmente todas las solicitudes válidas.

Para cada archivo ejecuta:

```text
IMetadataProductiveApplicationCoordinator.PrepareAsync
```

El resultado individual debe demostrar:

```text
VerifiedCopyWasPrepared = true
PromotionDecision = Pending
ErrorMessage vacío
```

antes de continuar.

El lote no modifica ningún original durante esta fase.

---

## Resultado de preparación batch

Se incorporó:

```text
MetadataProductiveBatchPreparationResult
```

para conservar:

- `BatchId`;
- inicio;
- fin;
- cantidad solicitada;
- resultados individuales preparados;
- cantidad de copias verificadas;
- mensajes auditables;
- estado de aborto y limpieza;
- disponibilidad para decisión global.

El lote solamente queda disponible para continuar cuando:

```text
IsReadyForDecision = true
```

Esto requiere que todas las solicitudes esperadas hayan generado una copia verificable pendiente.

---

## Fallo durante la preparación

La preparación conserva la política fail-fast.

Ejemplo:

```text
Archivo 1
→ preparado correctamente

Archivo 2
→ fallo durante PrepareAsync

Archivo 3
→ no iniciado
```

El coordinador no deja la preparación del archivo 1 abandonada.

Las preparaciones anteriores todavía pendientes son finalizadas automáticamente mediante:

```text
CompleteAsync(... Declined)
```

utilizando el coordinador productivo individual.

El resultado queda:

```text
WasAbortedAndCleanedUp = true
IsReadyForDecision = false
```

Esto impide presentar al usuario un lote parcialmente preparado como disponible para promoción.

---

## Primera confirmación de usuario

La acción `Revisar lote` solicita una primera confirmación antes de iniciar la preparación.

La interfaz informa:

- cantidad de archivos;
- cantidad de cambios;
- lista de archivos;
- cantidad de cambios por archivo;
- que los originales todavía no serán modificados.

Si el usuario cancela:

```text
ninguna preparación se crea
ningún original se modifica
```

---

## Segunda confirmación global

Después de una preparación satisfactoria:

```text
IsReadyForDecision = true
```

la interfaz solicita una segunda confirmación.

En este punto todas las copias ya fueron:

```text
creadas
→ modificadas
→ verificadas
→ preservadas
```

pero los originales continúan intactos.

La decisión global solamente puede ser:

```text
Approved
Declined
```

---

## Resultado de finalización batch

Se incorporó:

```text
MetadataProductiveBatchCompletionResult
```

para consolidar:

- identidad del lote;
- decisión global;
- cantidad solicitada;
- resultados procesados con la decisión;
- resultados de limpieza de recuperación;
- cantidad de éxitos;
- cantidad de fallos;
- duración;
- estado seguro de los originales;
- estado global de finalización;
- mensajes auditables.

El modelo distingue entre:

```text
DecisionResults
```

y:

```text
CleanupResults
```

para no confundir una promoción solicitada con una limpieza automática posterior a un fallo.

---

## Finalización Declined

Si el usuario rechaza la promoción global:

```text
CompleteAsync(
    preparationResult,
    MetadataPromotionDecision.Declined)
```

todas las preparaciones son finalizadas con `Declined`.

El coordinador individual:

- no promueve los originales;
- elimina los entornos aislados;
- mantiene los originales intactos;
- registra una finalización segura.

La validación real confirmó un lote de dos archivos:

```text
2 preparaciones verificadas
→ segunda confirmación = No
→ 2 de 2 procesadas con Declined
→ 0 fallos
→ originales en estado seguro
```

La selección productiva permanece disponible porque ningún archivo fue promovido.

---

## Finalización Approved

Si el usuario acepta la segunda confirmación:

```text
CompleteAsync(
    preparationResult,
    MetadataPromotionDecision.Approved)
```

las preparaciones son promovidas secuencialmente.

Cada archivo continúa utilizando las mismas garantías individuales:

```text
backup productivo
→ verificación del backup
→ staging
→ sustitución
→ verificación del destino
→ rollback individual si corresponde
→ limpieza
```

No se implementa una segunda lógica de escritura ni de promoción específica para batch.

---

## Primera promoción batch real

Se validó productivamente el flujo completo utilizando dos copias de archivos reales.

La secuencia confirmó:

```text
Solicitudes: 2
Cambios aprobados: 2
Preparaciones verificadas: 2 de 2
Lista para decisión global: Sí
Decisión global: Approved
Resultados procesados: 2 de 2
Resultados correctos: 2
Resultados fallidos: 0
Limpiezas de recuperación: 0
Originales en estado seguro: Sí
Resultado global correcto: Sí
```

Los dos archivos fueron promovidos correctamente.

---

## Fail-fast durante Approved

Si una promoción falla:

```text
Archivo 1 → Approved correcto
Archivo 2 → fallo
Archivo 3 → pendiente
```

la política es:

```text
conservar Archivo 1
detener nuevas promociones
limpiar preparaciones pendientes
```

Las preparaciones posteriores todavía pendientes son finalizadas automáticamente con:

```text
Declined
```

No existe rollback transaccional global de archivos ya promovidos.

La responsabilidad de rollback continúa perteneciendo a cada promoción individual.

---

## Limpieza después de fallos

Las operaciones de recuperación utilizan:

```text
CancellationToken.None
```

de forma intencional.

Una cancelación externa debe impedir iniciar nuevas promociones, pero no debe impedir eliminar entornos productivos aislados que ya fueron creados.

Esto evita dejar preparaciones verificadas huérfanas después de:

- cancelación;
- excepción;
- fallo de promoción;
- resultado individual no satisfactorio.

---

## Selección después de una promoción

Después de un `Approved`, solamente los archivos realmente promovidos son retirados de:

```text
ProductiveBatchSelection
```

Ejemplo:

```text
Archivo A → promovido
Archivo B → falla
Archivo C → no ejecutado
```

produce:

```text
A → eliminado de la selección
B → permanece
C → permanece
```

Esto permite revisar o reintentar los elementos no completados sin reconstruir todo el lote.

---

## Batch Post-Application Refresh

La aplicación productiva batch incorpora refresco automático después de una promoción.

Se añadió una operación que:

```text
identifica resultados WasSuccessfullyPromoted
→ relee cada archivo desde disco
→ sustituye su instancia en la tabla
→ actualiza ItemsSource una sola vez
→ restaura la selección
```

Esto evita ejecutar el refresco individual repetidamente para cada archivo.

---

## Preservación de la selección visible

Antes de refrescar las filas se conserva:

```text
selectedFilePath
```

Si el archivo seleccionado fue promovido, la interfaz selecciona la nueva instancia recién leída.

Si el archivo visible no pertenecía a los promovidos, se conserva su selección existente.

De esta manera el batch no fuerza al usuario a cambiar de contexto después de la operación.

---

## Reconstrucción del plan seleccionado

Si el archivo actualmente seleccionado fue promovido correctamente, el sistema reutiliza:

```text
AnalyzeSelectedFileAsync(
    FileAnalysisInvocation.PostApplicationRefresh)
```

para reconstruir su plan desde los metadatos persistidos.

El refresco reutiliza la infraestructura creada en el Milestone 13.29.

No se ejecutan automáticamente búsquedas completas para todos los archivos promovidos.

Las demás filas ya están actualizadas desde disco y sus planes se reconstruirán cuando el usuario las analice.

Esto evita búsquedas externas innecesarias durante una única aplicación batch.

---

Después de promover dos archivos se confirmó:

```text

Fila actualizada desde el archivo promovido: archivo 2
```

```text

```

confirmando que la interfaz utiliza el contenido físico posterior a la promoción.

## Coordinador productivo simulado reutilizable

La infraestructura de pruebas fue refactorizada para incorporar:

```text
RecordingProductiveApplicationCoordinator
```

como coordinador controlado compartido.

Permite simular:

- resultados fallidos;
- decisiones registradas;
- conteos de ejecución;
- cancelación controlada.

Esto evita duplicar coordinadores simulados entre los distintos runners batch.

## Valores diagnósticos no constantes

Durante la revalidación final se detectó una fragilidad histórica en varios tests productivos.

Los diagnósticos utilizaban:

```text
Electronic
```

como género fijo.

Después de ejecutar promociones reales, algunos archivos ya contenían `Electronic`.

Eso provocaba:

```text
valor original = Electronic
valor solicitado = Electronic
```

por lo que:

```text
hash inicial = hash final
```

y los tests interpretaban correctamente que no había existido una modificación física.

El problema no pertenecía al pipeline productivo sino a los datos de prueba.

Se incorporó:

```text
DiagnosticMetadataTestValues
```

para generar valores diferentes en cada ejecución:

```text
AudioMetadataManager Diagnostic <Guid>
```

Las constantes de prueba que requieren valores generados en tiempo de ejecución fueron convertidas a:

```text
static readonly
```

cuando correspondía.

Los parámetros opcionales conservaron constantes válidas de compilación y generan el valor variable dentro del flujo de ejecución cuando es necesario.

## Garantías de seguridad preservadas

El milestone mantiene las reglas fundamentales del sistema:

```text
ninguna escritura productiva sin backup
ninguna promoción sin copia verificada
ninguna sustitución sin segunda confirmación
ningún lote continúa después del primer fallo
ninguna preparación pendiente se abandona después de un fallo
ningún rollback global modifica archivos anteriormente completados
```

La seguridad individual continúa teniendo prioridad sobre la coordinación batch.

---

## Comportamiento final de la interfaz

El flujo productivo batch final es:

```text
analizar archivo A
→ aprobar cambios

analizar archivo B
→ aprobar cambios

Lote productivo: 2 archivos · N cambios

→ Revisar lote

Primera confirmación
→ preparar

PrepareAsync batch
→ todas las copias verificadas
→ originales intactos

Segunda confirmación

No
→ Declined para todas las preparaciones
→ originales intactos

Sí
→ Approved secuencial
→ backups
→ promoción
→ verificación
→ rollback individual si corresponde
→ limpieza
→ retiro de elementos promovidos
→ relectura de filas
→ reconstrucción del plan seleccionado
```

---

## Resultado del milestone

Audio Metadata Manager dispone ahora de un flujo productivo multiarchivo completamente integrado con la interfaz y protegido por dos confirmaciones.

El sistema puede:

- acumular planes aprobados de diferentes archivos;
- construir una solicitud productiva batch;
- preparar todas las copias antes de pedir permiso para modificar originales;
- rechazar globalmente el lote sin modificar originales;
- promover múltiples archivos secuencialmente;
- detener promociones después del primer fallo;
- limpiar preparaciones pendientes;
- conservar resultados ya promovidos;
- mantener pendientes los archivos no completados;
- actualizar la selección batch;
- releer los archivos promovidos desde disco;
- actualizar las filas visibles;
- reconstruir el plan del archivo seleccionado;
- ejecutar repetidamente el diagnóstico sin depender de un género fijo.

El Milestone 13.31 deja preparada la aplicación para futuras capacidades de gestión batch más avanzadas, como revisión dedicada del contenido del lote, reintentos selectivos, persistencia del estado batch y operaciones masivas sobre bibliotecas completas.
